# Characterization record — legacy behaviour vs. intent (WU-M1-14)

Consolidated record of observed legacy behaviour, derived exclusively from the ten
committed journey specs (`e2e/journeys/j01-*.spec.ts` … `j10-*.spec.ts`), which were
themselves derived by **reading** `legacy/lib/` — never by observing a running system.
Every entry below traces to a `// src:` citation already present in a spec, or to a
named decision in `docs/plans/2026-08-18-democracyos-grill-decisions.md` /
`docs/plans/2026-08-18-democracyos-revival-plan.md`. Nothing here is invented.

## 1. Purpose and how to use this document

This is the **intent-vs-behaviour record** for the rebuild (plan §4.2, WU-M1-14).

**The rule:** a legacy bug is **never reimplemented faithfully**, and **every deviation
from legacy behaviour must appear in this document** — either as a defect-register row
with its intended behaviour, or as a new-behaviour entry citing its decision. A spec
assertion is never quietly edited to match an implementation; per `e2e/SPEC-LEDGER.md`,
an assertion edit is a reviewed change to this document first.

How to use it, by audience:

- **Implementers** (M3–M6): before building a feature, read its domain section (§2) for
  the behaviour to preserve, §3 for the bugs you must NOT rebuild (each row states the
  intended behaviour), §4 for the odd-looking behaviour you must NOT "fix", and §5 for
  the new requirements with no legacy analogue.
- **Reviewers**: a diff that reproduces a §3 row is a defect; a diff that removes a §4
  row is a regression; a deviation from legacy that appears in neither §3 nor §5 is an
  undocumented change and must be added here (reviewed) before it merges.
- **Activation WUs** (M4/M5): §6 lists the open questions each activation must resolve
  (final Romanian copy is recorded HERE at activation), §7 the fixture/infrastructure
  gaps that block flipping a spec from pending to active.

Citation convention: `file:lines` refers to paths under `legacy/` exactly as cited in
the owning spec. "Owner" is the journey of record; cross-referencing journeys are
listed as x-ref and defer to the owner (SPEC-LEDGER rule: deduplicate to the owner).
